# Suppression report contract

Run the planner with:

`node /app/bin/suppression-cli.js --events /absolute/events.jsonl --as-of 2026-06-01T00:00:00Z --out /absolute/report.json`

The events file is newline-delimited JSON. Valid rows have string `event_id`, string `email`, string `type`, and ISO-8601 UTC `timestamp`. Supported `type` values are `bounce`, `complaint`, `unsubscribe`, and `resubscribe`. `unsubscribe` rows require a non-empty string `list_id`. `resubscribe` may include a non-empty `list_id`; if omitted, it is a global resubscribe. `bounce` rows use `subtype: "hard"` or `subtype: "soft"`; a missing subtype is treated as `hard`. `expiry_days`, when present, must be an integer greater than or equal to zero. Email identity is `email.trim().toLowerCase()`; do not remove plus tags or rewrite dots.

Rows are validated in file order. Invalid JSON, missing required fields, invalid emails, invalid timestamps, unknown types, missing unsubscribe lists, and unknown bounce subtypes are rejected with warnings and do not create recipients. For invalid JSON warnings, preserve the complete raw input line as `detail`, including leading or trailing spaces. An invalid `expiry_days` value does not reject an otherwise valid row; it is ignored, the row still goes through duplicate and future-event handling, and the normal default or no-expiration rule is used. If two valid rows have the same `event_id`, the first valid row in the file wins and each later valid duplicate is ignored with a `duplicate_event` warning. Invalid rows do not reserve an `event_id`, but future rows do because duplicate filtering happens before the future-event filter. For example, if line 1 is a valid future event with `event_id: "move-1"` and line 2 is a past event with the same id, line 1 gets a `future_event` warning and line 2 gets a `duplicate_event` warning; neither row creates a recipient. After validation and duplicate filtering, events are applied by ascending timestamp; events with the same timestamp are applied by ascending original line number. Events after `--as-of` are ignored with a `future_event` warning. Expiration uses a half-open window: a reason with `expires_at` is active only when `as_of < expires_at`; it is inactive at exactly `expires_at`.

Suppression reasons:

- `complaint`: global, permanent, never cleared by resubscribe.
- `hard_bounce`: global, expires after 180 days unless `expiry_days` is present, never cleared by resubscribe before expiry.
- `soft_bounce`: global, expires after 14 days unless `expiry_days` is present, cleared by any later valid resubscribe for the recipient.
- `unsubscribe`: list scoped as `list:<list_id>`, no expiration unless `expiry_days` is present, cleared by a later valid resubscribe for the same `list_id`; a global resubscribe clears all unsubscribe reasons for the recipient.

When a new active reason has the same `email`, `code`, and `scope` as an existing reason, the later event replaces the previous one. Resubscribe never creates its own report reason.

The output JSON must contain exactly these top-level keys in this order: `as_of`, `summary`, `recipients`, `warnings`. `summary` has keys `total_recipients`, `suppressed_recipients`, `warning_count`, and `active_reason_counts`. `active_reason_counts` has keys `complaint`, `hard_bounce`, `soft_bounce`, and `unsubscribe`, counting active reason objects, not unique recipients. `recipients` is sorted by `email` and includes every recipient with at least one valid, non-future event at or before `as_of`. Each recipient object has keys `email`, `suppressed`, and `reasons`. Reasons are sorted by code order `complaint`, `hard_bounce`, `soft_bounce`, `unsubscribe`, then `scope`, `since`, and `event_id`. Each reason has keys `code`, `scope`, `event_id`, `since`, and `expires_at`; `expires_at` is either an ISO string or `null`.

Warnings are sorted by ascending `line`, then `code`, then `event_id`. Each warning has keys `code`, `line`, `event_id`, and `detail`. Use these codes: `invalid_json`, `missing_event_id`, `missing_email`, `invalid_email`, `invalid_timestamp`, `unknown_type`, `missing_list`, `unknown_bounce_subtype`, `invalid_expiry_days`, `duplicate_event`, and `future_event`. `detail` is always a string. For `invalid_json`, use the raw invalid line text. For `missing_event_id`, the detail value is the literal string `event_id`. For `missing_email`, use the raw email value when present or an empty string when absent. For `invalid_email`, `invalid_timestamp`, `unknown_type`, `unknown_bounce_subtype`, and `invalid_expiry_days`, use the rejected raw value converted to a string. For `missing_list`, the detail value is the literal string `list_id`. For `duplicate_event`, use the winning event id. For `future_event`, use the ignored timestamp normalized to an ISO string such as `2026-07-01T00:00:00.000Z`.
