# إنشاء سياسة أمان المحتوى

تُعد سياسة CSP وسيلة دفاع إضافية متعددة الطبقات يفرضها المتصفح. وهي تحدد البرامج النصية والأنماط والموارد الأخرى المسموح بتحميلها، حتى عندما لا يكون تحويل الأحرف الخاصة في مخرجات HTML إلى صيغة آمنة مكتملا.

## مبادئ التصميم

- ابدأ بالسياسة الأكثر تقييدًا التي يستطيع التطبيق العمل معها، ثم أضف الاستثناءات فقط عند وجود حاجة مثبتة إليها.
- اعتبر `default-src 'self'` نقطة انطلاق، وليس دليلًا على أن `script-src` آمن.
- أعطِ الأولوية لإزالة `unsafe-inline` و`unsafe-eval` ومصادر أحرف البدل بدلًا من إضافة قوائم سماح جديدة.



## مرجع التوجيهات

| التوجيه | بماذا يتحكم |
|-----------|------------------|
| `default-src` | الخيار البديل عند غياب التوجيهات الأخرى |
| `script-src` | تنفيذ JavaScript (الأهم للحماية من XSS) |
| `style-src` | أوراق الأنماط وسلوك الأنماط المضمنة |
| `frame-ancestors` | اختطاف النقرات عبر التضمين  |
| `form-action` | حيث يمكن تقديم النماذج |
| `base-uri` |  `<base href>` الوجهات الصالحة ل|


## مراجعة سياسة موجودة

راجع الأسئلة التالية بالترتيب:

1. هل يستخدم أي توجيه `*`؟
2. هل يسمح `script-src` باستخدام `unsafe-inline` أو `unsafe-eval`؟
3. هل يفرض `default-src` قيودًا صارمة بينما لا يزال `script-src` متساهلًا؟
4. هل تتضمن السياسة نطاقات تابعة لجهات خارجية لم يعد التطبيق يستخدمها؟

وثّق الغرض من كل استثناء قبل ابقائه.


## تنفيذ التغييرات

عند تعديل سياسة مستخدمة بالفعل:

1. فكّر أولًا في استخدام وضع الإبلاغ فقط لجمع  الانتهاكات دون حظر المستخدمين.
2. أصلح المشكلات الناتجة عن التغييرات (مثل معالجات الأحداث المضمّنة و CDNs غير متوقعة) قبل فرض السياسة.
3. أعد اختبار مسارات الاستخدام الأساسية بعد فرض السياسة.

## التكامل مع مراجعة الشيفرة

يُكمل تعزيز سياسة CSP عملية تتبّع مدخلات المستخدم حتى وصولها إلى HTML، والتحقق من وجهات إعادة التوجيه، ومراجعة إعدادات ملفات تعريف الارتباط الخاصة بالجلسات، ولا يحل محلها. استخدم هذه المهارة عندما تكون المخاطر المتبقية مرتبطة ببنية السياسة وإعداداتها، وليس عندما تكون المشكلة الأساسية هي عرض بيانات مخزّنة في القوالب دون تحويل أحرفها الخاصة إلى صيغة آمنة.
