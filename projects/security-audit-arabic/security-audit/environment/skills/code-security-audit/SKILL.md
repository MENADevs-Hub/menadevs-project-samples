# تدقيق أمان الشيفرة البرمجية

طريقة منظمة لتدقيق شيفرة التطبيقات وتقديم نتائج أمنية قابلة للتنفيذ. الهدف هو الحصول على نتائج بدرجة عالية من الثقة - تحديد الثغرات الحقيقية وتجاهل النتائج غير المهمة.

## سير عمل التدقيق

### المرحلة 1: فهم التطبيق

قبل البحث عن الأخطاء، افهم ما يفعله التطبيق وأين تقع حدود الثقة. اقرأ نقطة الدخول، وحدد المسارات، وتعرّف على ما يلي:

- أين تدخل مدخلات المستخدم؟ (معاملات الاستعلام، بيانات النماذج، العناوين، ملفات تعريف الارتباط، الملفات المرفوعة)
- أين تخرج البيانات؟ (قوالب HTML، استجابات JSON،  إعادات التوجيه، السجلات)
- ما العمليات الحساسة الموجودة؟ (المصادقة، والتحكم في الصلاحيات، والوصول إلى الملفات، واستعلامات قواعد البيانات)
- ما ضوابط الأمان المطبقة بالفعل؟ (البرمجيات الوسيطة، وتنقية المدخلات، وترويسات CSP)

هذا مهم لأن الثغرات تظهر عند حدود الثقة - في المواضع التي تنتقل فيها البيانات غير الموثوقة إلى سياق موثوق.

### المرحلة 2: المراجعة المنهجية حسب الفئة

تعامل مع الفئات التالية حسب ترتيب الأولوية. لكل فئة، تتبع تدفق البيانات من الإدخال إلى الإخراج، وابحث عن عمليات التحقق أو تحويل الأحرف الخاصة المفقودة.

**حماية المدخلات والمخرجات (CRITICAL)**
- الحقن: ثغرات XSS (المنعكسة والمخزنة)، وحقن SQL، وحقن الأوامر، وحقن القوالب
- ابحث عن مدخلات المستخدم التي تُعرض في HTML دون تحويل الأحرف الخاصة إلى صيغة آمنة - وتتبع كل مسار من الإدخال إلى الإخراج، بما في ذلك المسارات غير المباشرة التي تُخزّن فيها البيانات قبل عرضها

**المصادقة وإدارة الجلسات (CRITICAL)**
- خصائص ملفات تعريف الارتباط الخاصة بالجلسات: HttpOnly وSecure وSameSite
- في Flask: اضبط `SESSION_COOKIE_HTTPONLY = True` و`SESSION_COOKIE_SAMESITE = "Lax"` في app.config
- تثبيت الجلسات، ومعرّفات الجلسات الضعيفة (IDs)
- تخزين كلمات المرور (التجزئة، وإضافة قيم عشوائية للتجزئة)


**التحكم في الوصول وإعادة التوجيه (HIGH)**
- إعادة التوجيه المفتوحة: هل يتحقق التطبيق من وجهات إعادة التوجيه باستخدام قائمة سماح؟
- اسمح فقط بالمسارات النسبية التي تبدأ بـ `/` (ولكن ليس `//`) والنطاقات الموثوقة
- ارفض عناوين URL الخارجية، وعناوين URL النسبية للبروتوكول (`//evil.com`)، ومعرّفات URI التي تستخدم `javascript:`
- أرجع HTTP 400 للوجهات غير الصالحة
- التحقق من الصلاحيات على نقاط النهاية الحساسة
- ثغرات IDOR (المراجع المباشرة غير الآمنة للكائنات)

**إعدادات الأمان (HIGH)**
- سياسة أمان المحتوى: هل تفرض قيودًا صارمة؟ انتبه إلى `unsafe-inline` و`unsafe-eval` ومصادر أحرف البدل `*`
- ترويسات أمان HTTP — تأكد من ضبط جميع الترويسات التالية: X-Frame-Options وX-Content-Type-Options وReferrer-Policy
- وضع تصحيح الأخطاء، ورسائل الأخطاء التفصيلية، وكشف المعلومات

**حماية البيانات (MEDIUM)**
- البيانات الحساسة في السجلات أو استجابات الأخطاء
- الأسرار أو بيانات الاعتماد المضمّنة مباشرة في الشيفرة
- غياب التشفير للبيانات الحساسة أثناء نقلها أو تخزينها

### المرحلة 3: التحقق من النتائج

لكل مشكلة محتملة، تأكد من أنها حقيقية:

1. تتبّع تدفق البيانات بالكامل من المصدر إلى نقطة الاستخدام
2. تحقق مما إذا كانت ضوابط الأمان الموجودة (تحويل الأحرف الخاصة، والتحقق من المدخلات، والبرمجيات الوسيطة) تعالج المشكلة بالفعل
3. قيّم قابلية الاستغلال — هل يستطيع المهاجم بالفعل استغلال هذه المشكلة عمليًا؟
4. حدّد درجة الثقة (1-10)؛ لا تُبلّغ إلا عن النتائج التي تبلغ درجة الثقة فيها 8 أو أكثر

تُعد عملية التصفية هذه مهمة لأن النتائج الإيجابية الخاطئة تُضعف الثقة في التدقيق. من الأفضل الإبلاغ عن 5 مشكلات حقيقية بدلًا من 20 مشكلة غير مؤكدة.

### المرحلة 4: الإصلاح والتحقق

لكل ثغرة مؤكدة:

1. نفّذ الإصلاح في شيفرة التطبيق
2. اكتب اختبار تراجع يثبت أن الثغرة قد أُزيلت (يجب أن يفشل الاختبار على الشيفرة القديمة وينجح على الشيفرة بعد إصلاحها)
3. تحقق من أن الإصلاح لا يؤثر على الوظائف الحالية

## تنسيق المخرجات

### تنسيق كل نتيجة

```markdown
## Finding: [Category] — [Brief Description]

**Severity:** CRITICAL | HIGH | MEDIUM
**Location:** `file.py:42`
**Confidence:** 9/10

### Root Cause
What makes this code vulnerable and why it matters.

### Remediation
What was changed to fix it, with code reference.
```
### هيكل التقرير

عند إنشاء تقرير أمني، نظّم النتائج حسب مستوى الخطورة، وأدرج ما يلي:

- ملخص تنفيذي لنطاق التدقيق ونتائجه
- كل نتيجة مع مستوى خطورتها، وسببها الجذري، وطريقة معالجتها
- ملخص للتحسينات الأمنية التي أُجريت

## إرشادات تحديد مستوى الخطورة

- **CRITICAL**: قابل للاستغلال مباشرة — ثغرات XSS، وحقن SQL، وتنفيذ الشيفرة عن بُعد (RCE)، وتجاوز المصادقة
- **HIGH**: قابل للاستغلال في ظروف محددة — إعادة التوجيه المفتوحة، وغياب ترويسات الأمان، وإعدادات الجلسات غير الآمنة
- **MEDIUM**: تأثير محدود — كشف المعلومات، وعدم تطبيق أفضل الممارسات

تجاهل النتائج ذات مستوى الخطورة LOW. يجب أن يُبرز التدقيق المشكلات المهمة.


## مرجع تعزيز أمان Flask

عند تدقيق تطبيق Flask، طبّق الإصلاحات التالية:

**XSS — escape at output:**
```python
from markupsafe import escape
# Every place user/session data appears in HTML:
safe_value = escape(user_input)
```

**Security headers — after_request hook:**
```python
@app.after_request
def add_security_headers(response):
    response.headers["Content-Security-Policy"] = "default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:"
    response.headers["X-Frame-Options"] = "DENY"
    response.headers["X-Content-Type-Options"] = "nosniff"
    response.headers["Referrer-Policy"] = "strict-origin-when-cross-origin"
    return response
```

**Session cookie hardening:**
```python
app.config["SESSION_COOKIE_HTTPONLY"] = True
app.config["SESSION_COOKIE_SAMESITE"] = "Lax"
```

**Redirect validation:**
```python
from urllib.parse import urlparse

def is_safe_redirect(target):
    if target.startswith("/") and not target.startswith("//"):
        return True  # internal path
    parsed = urlparse(target)
    if parsed.scheme not in ("http", "https"):
        return False
    return parsed.hostname in TRUSTED_HOSTS
```


## المبادئ الأساسية

1. تتبّع تدفق البيانات من الإدخال إلى الإخراج — تنشأ معظم الثغرات بسبب غياب تنقية المدخلات عند حدود الثقة
2. افحص مسارات البيانات المخزّنة والمنعكسة بشكل منفصل — فالبيانات المخزّنة التي تُعرض في HTML خطيرة بقدر المدخلات المنعكسة، ولكن يسهل إغفالها لأن الإدخال والإخراج يحدثان في طلبين مختلفين
3. تحقق من وجهات إعادة التوجيه باستخدام قوائم السماح، وليس قوائم الحظر — فقوائم الحظر تحتوي دائمًا على ثغرات
4. ترويسات الأمان هي وسيلة دفاع إضافية متعددة الطبقات — فهي لا تحل محل إصلاح الشيفرة، لكنها تحدّ من نطاق الضرر عندما تمر مشكلة دون اكتشافها
5. أعطِ الأولوية لدرجة الثقة العالية بدلًا من كثرة النتائج -  نتائج حقيقية أفضل من 20 نتيجة إيجابية خاطئة
